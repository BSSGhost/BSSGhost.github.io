1. NOUVEAUX FICHIERS CRÉÉS
----------------------------
- database/migrations/admin-system.sql : Migration SQL complète
  * 5 tables : roles, permissions, role_permissions, admin_users, audit_logs
  * 34 permissions au total (étudiants, professeurs, classes, matières, notes, rapports, admins, rôles, paramètres, audit, sessions)

  * 2 administrateurs initiaux : DEthiam@sunu-moyenne.com et Colonelgueye@sunu-moyenne.com

- backend/services/auth.service.js : Service d'authentification
  * Hashage bcrypt avec 12 rounds (SALT_ROUNDS)
  * Comparaison mot de passe via bcrypt.compare()
  * Génération JWT avec jsonwebtoken
  * Secret lu depuis process.env.JWT_SECRET
  * Durée token : 24h
  * Fonctions : hashPassword, comparePassword, generateToken, verifyToken
  * Middleware adminAuthMiddleware et permissionMiddleware
  * Enregistrement audit via recordAuditAction

- backend/services/admin.service.js : Couche service administration
  * loginAdmin(email, plainPassword) - connexion avec gestion must_change_password
  * logoutAdmin() - déconnexion
  * getMe(adminId) - profil administrateur
  * changePassword(adminId, oldPassword, newPassword) - changement de mot de passe
  * createAdmin(adminData, creatorId) - création d'un nouvel admin (principal seulement)
  * updateAdmin(adminId, updates, modifierId) - modification dadmin
  * disableAdmin(adminId, modifierId) - désactivation (protège principal)
  * enableAdmin(adminId, modifierId) - réactivation
  * listAdmins() - liste des admins avec détails

- backend/middleware/adminAuth.js : Middleware d'authentification
  * Vérification token JWT depuis en-tête Authorization ou cookie
  * Vérification administrateur actif en base
  * Détection compte désactivé
  * (Initialement conçu comme middleware Express)

- backend/middleware/permissions.js : Middleware de vérification RBAC
  * verifyPermission(permissionName) - vérification de permission stricte
  * verifyAnyPermission(allowedPermissions) - vérification "au moins une"
  * getUserPermissions(adminId) - récupération permissions depuis DB
  * (Ancienne getUserPermissions corrigée : plus de req non défini)

- backend/routes/admin.routes.js : Routes API administration
  * POST /api/admin/login - connexion
  * POST /api/admin/logout - déconnexion
  * GET /api/admin/me - profil
  * POST /api/admin/change-password - changement mot de passe
  * GET/POST /api/admin/users - liste/création admins (principal seulement)
  * PUT /api/admin/users/:id - modification admin (principal seulement)
  * PUT /api/admin/users/:id/disable - désactivation (protège principal)
  * PUT /api/admin/users/:id/enable - réactivation
  * GET /api/admin/audit/logs - journal d'activité (principal seulement)
  * POST /api/admin/audit/clear - vidage journal (principal seulement)

- admin/index.html : Interface administration moderne et responsive

- admin/admin.js : Logique client administration

  * Écran connexion si non connecté

  * Fonction logoutAdmin() - déconnexion
  * Gestion erreurs affichage

- server.js : Serveur Node/Express restructuré

7. SYSTÈME MUST_CHANGE_PASSWORD
---------------------------------
Déroulement première connexion :
1. Connexion avec LYNAQE123@
2. Serveur vérifie password_hash NULL en base
3. Hashage bcrypt du mot de passe, mise à jour base
4. Retour { must_change_password: true, user: {...} }
5. Écran frontend s'affiche : "Changer votre mot de passe"
6. Formulaire : ancien mot de passe + nouveau + confirmation
7. Soumission → POST /api/admin/change-password avec oldPassword réel
8. Serveur vérifie oldPassword via bcrypt.compare
9. Hashage nouveau mot de passe, mise à jour base, must_change_password = false
10. Token JWT normal émis, accès complet dashboard

Contournement impossible :
- Côté serveur : vérification must_change_password à chaque requête authentifiée
- Côté frontend : affichage obligé de l'écran de changement
- API directe : renvoie must_change_password: true, pas d'accès aux APIs protégées

8. SÉCURITÉ COOKIE ET JWT
--------------------------
- Cookie admin_token défini par serveur via res.cookie()
- HttpOnly: true (interdit accès par JS côté client)
- Secure: true en production (NODE_ENV === 'production')
- SameSite: strict
- Max-Age: 24 heures
- Chemin: racine (/)

- JWT_SECRET lu depuis variables d'environnement
- Valeur par défaut 'sunu-moyenne-admin-secret-change-in-production' seulement en dev
- En production, démarrage refusé si JWT_SECRET absent ou valeur par défaut
- Payload JWT : { id, email, role, permissions }
- Signature JWT vérifiée à chaque requête protégée
- Token jamais stocké en localStorage (utilisé seulement en mémoire/curseur)

9. PROTECTION CONTRE LES TENTATIVES DE CONNEXION
--------------------------------------------------
- Limite : 5 tentatives échouées par email
- Blocage : 15 minutes
- Pendant le blocage, toutes les tentatives sont comptabilisées
- Après expiration, compteur réinitialisé
- Aucun message ne révèle si l'email existe ou non
- Erreur générique "trop de tentatives" affichée
